# SHEAR GPU 线程利用率：潜在优化点与验证思路

代码核对日期：2026-10-18。

本文整理当前 SHEAR 实现中值得进一步检查的 GPU 执行效率问题，覆盖 leader 数量与叶块粒度，以及距离计算、候选筛选、成员分发、结果合并、任务调度、数据布局和分支分歧。目标是在保持检索质量的前提下，提高有效计算吞吐、缩短整体构建时间。

文中的“当前实现”主要指常驻内核的大分区协作路径和通用 SQ8 WMMA 叶块计算路径。可选的专用内核可能采用不同的线程分工，不能将某条路径的观察直接推广到所有后端。本文没有运行新的性能实验；代码行为、可能的性能影响和待验证的改进方案分别说明。

## 1. 阅读这些优化点前，需要明确的边界

### 1.1 线程活跃不等于有效吞吐高

需要区分三种情况：

- **没有有效工作：**某些 lane 或 warp 没有对应的数据，或者队列中没有就绪任务。
- **有工作但暂时无法推进：**等待数据、同步、锁或其他任务完成。
- **在执行但有效产出较少：**计算填充位置、重复计算、反复轮询等。

让更多线程活跃并不自动缩短运行时间。增加线程协作可能引入通信、同步和资源开销，扩大叶块也会增加距离计算量。最终要同时观察时间、有效计算量和检索质量。

### 1.2 当前叶块配置与执行任务的大小

四数据集运行说明使用 `--leaf-size-min 256 --leaf-size-max 1280`。但当前常驻内核的规划是：

```text
leaf_min    = 64
leaf_target = 128
leaf_max    = max(256, params.c_max)
```

在上述运行配置下，`leaf_max=1280`。`leaf_min` 用于部分小节点路径的小块合并，不是所有叶块的硬下限；大分区路径会直接发布非空且不超过 `leaf_max` 的子块，可能产生小于 64 或 256 的叶块。当前节点处理函数也没有把 `leaf_target` 用于决定 leader 数量。

另外，完整叶块和单个 CTA 领取的任务不同：默认每个叶块任务最多覆盖 128 个源点；`row-owned` 扫描整个叶块的候选，`staged` 在叶块超过 512 个成员时进一步将候选列拆为最多 128 个成员一段。WMMA 内部仍按 16×16 的源点—目标块处理，沿维度分片累加。

依据：[运行参数](/home/wbh/rswork/SHEAR/docs/runbooks/p1_p2_shear_four_dataset.md:691)、[常驻内核规划](/home/wbh/rswork/SHEAR/shear-core/src/algorithm/pipnn/compute_backend.rs:1326)、[叶块任务拆分](/home/wbh/rswork/SHEAR/shear-core/src/algorithm/pipnn/compute_backend.rs:11782)。

## 2. 优化点概览

| 优化点 | 当前可确认的行为 | 需要验证的影响 | 可能的优化方向 |
|---|---|---|---|
| leader 数量与叶块粒度 | 数量主要由采样比例、规模和深度决定 | 是否产生过多小叶块，影响有效并行与候选覆盖 | 将 fanout、目标叶块大小和维度纳入决策 |
| WMMA 后的距离恢复与 top-k | 通用路径主要由每个 warp 的前 16 个线程逐行处理 | 后处理是否限制计算吞吐 | 调整结果分工、针对小 k 优化 |
| 分区计数、偏移与分发 | 不同阶段使用的线程数明显不同 | 搬运、原子竞争和同步是否造成等待 | 批量分发、聚合计数、减少同步 |
| 工作领取与尾部任务 | CTA 批量领取，warp 没有独立补充任务 | 尾部不足、边界填充和长任务是否造成浪费 | 调整任务粒度、小任务合批 |
| staged 结果合并 | 同源点的局部 top-k 通过行锁合并 | 并行任务增加是否被合并成本抵消 | 自适应选择执行模式、改进归并方式 |
| 生产者—消费者调度 | 候选 CTA 可协助大分区，但帮助受阶段限制 | 队列空闲和执行尾部是否限制吞吐 | 调整任务供给、协作时机与执行顺序 |
| 数据加载与资源占用 | 按成员 ID 取向量，使用共享内存和中间数组 | 数据等待、资源限制是否降低并行推进能力 | 复用数据、重叠加载与计算、压缩状态 |
| WMMA 结果矩阵布局 | 结果按行存储，相邻线程跨行读取同一列 | 按源码地址映射存在共享内存 bank 冲突风险 | 对照测试列式结果存储与匹配读取 |
| 分区中的分支分歧 | top-r 插入、移动和 tie-break 依赖各源点的数据 | 同一 warp 的不同执行路径是否造成明显开销 | 针对常用 fanout 简化路径，核对机器指令 |

以上是待研究的方向，不是已经测得收益的优化清单，也不是按已知耗时排序。

## 3. leader 数量没有直接对齐目标叶块大小

**当前做法。**普通大分区首次选点前，先计算 `round(N × 有效采样比例)`，再应用数量上限。当前运行配置的基础比例为 5%，有效比例会根据节点大小和深度调整。leader 数量的计算没有直接使用期望叶块大小，也没有按 fanout 对预期子块大小进行校准。

例如，1290 个成员、有效比例为 4% 时，初步得到 52 个 leader。若分配均衡、52 个子分区均非空：

| fanout | 预期成员归属总数 | 平均子分区大小 |
|---|---:|---:|
| 3 | 3870 | 约 74 |
| 1 | 1290 | 约 25 |

这里是用于理解规模的估算，不是运行中测得的叶块分布。

**可能的问题。**小叶块可能使一个 CTA 内只有少量 warp 承担有效计算，调度与同步开销更难摊薄；同时，每个点接触到的块内候选范围也会改变。但小叶块能够减少两两距离计算，因此不能单凭叶块小就断言性能差。

**优化思路。**引入期望平均叶块大小 `T`，用 `ceil(N × fanout / T)` 作为候选估计，再结合维度、数量上限和划分不均衡程度调整。也可评估在发布叶块前合并过小子块。这个公式只是待测试的启发式，不保证空间质量、最大子块大小或最佳运行时间。

**预期目标。**平衡叶块内有效并行、叶块任务数量、总距离计算量和候选覆盖。

**验证指标。**叶块大小直方图、小叶块比例、候选距离计算次数、任务数量、GPU 时间、整体构建时间及相同搜索配置下的召回率/QPS。修改 leader 数量会改变候选集合，不能只做等输出比较或只测内核速度。

依据：[采样比例调整](/home/wbh/rswork/SHEAR/shear-core/src/algorithm/pipnn/compute_backend.rs:7044)、[leader 数量与初始选点](/home/wbh/rswork/SHEAR/shear-core/src/algorithm/pipnn/compute_backend.rs:12515)、[大分区发布子块](/home/wbh/rswork/SHEAR/shear-core/src/algorithm/pipnn/compute_backend.rs:15668)。

## 4. WMMA 后的距离恢复与 top-k 筛选

**当前做法。**32 个线程协作完成 WMMA，随后将结果存入共享内存。通用 SQ8 叶块路径中，主要由每个 warp 的前 16 个线程各负责一个源点，顺序读取该源点对应的各列结果、恢复近似距离并更新小型 top-k 状态。分区的 top-r 维护也使用类似的逐行处理方式。

```text
线程 0  → 源点 0：逐列比较并维护 top-k
线程 1  → 源点 1：逐列比较并维护 top-k
……
线程 15 → 源点 15：逐列比较并维护 top-k
线程 16～31 不参与这段逐行结果处理
```

**可能的问题。**后处理阶段只有部分 lane 执行有效工作；同一个源点的候选比较、插入和数组移动存在顺序依赖。不能据此说整个 warp、整个内核或 Tensor Core 阶段的利用率只有 50%。

**优化思路。**比较更多 lane 协作处理结果、分组选择后归并，以及针对固定小 k 的专用实现。当前已有可选的 D96/K2 专用路径，进一步优化前应先核对适用条件和已有实现，避免重复设计。

**预期目标。**降低每个有效距离结果的处理成本，使矩阵计算和候选筛选衔接更高效。

**验证指标。**后处理指令与时间、活跃 lane、通信与同步开销、每秒有效候选处理量，以及候选 ID/距离的正确性。当前常用 `k=2`，顺序维护本身很短；更多线程协作不一定更快。

依据：[通用 SQ8 结果处理](/home/wbh/rswork/SHEAR/shear-core/src/algorithm/pipnn/compute_backend.rs:10046)、[候选插入](/home/wbh/rswork/SHEAR/shear-core/src/algorithm/pipnn/compute_backend.rs:8068)、[叶块模式选择](/home/wbh/rswork/SHEAR/shear-core/src/algorithm/pipnn/compute_backend.rs:578)。

## 5. 分区计数、偏移计算与成员分发

**当前做法。**常驻内核的大分区协作分为 COUNT、EMIT、SCATTER、PUBLISH 等阶段。各阶段的线程分工并不相同：

| 操作 | 当前线程分工 |
|---|---|
| COUNT 中的矩阵计算 | batch-8 最多给 8 个 warp 各分配一个 16 行成员块 |
| COUNT 中的计数提交 | 最多 128 个成员按线程分配，更新各子分区的原子计数 |
| EMIT 中的偏移计算 | 获得处理权的 CTA 由线程 0 遍历各子分区并计算偏移 |
| SCATTER 中的成员分发 | 虽然批量领取多个块，仍逐块处理；每块最多 16 个线程读取和写入成员 ID |
| PUBLISH 中的子任务发布 | 获得发布权的 CTA 由线程 0 组织子任务并发布 |

**可能的问题。**batch-8 改善了距离计算阶段的工作分配，但 SCATTER 没有对应地让 8 个块同时搬运。逐块处理伴随多次 CTA 同步；计数和写位置使用原子操作，成员集中到少数子分区时可能竞争。偏移与发布阶段的串行部分也可能延迟后续任务就绪。

**优化思路。**将一整批成员展开到更多线程并行分发；评估 CTA/warp 内聚合计数后再提交，或批量申请子分区写入区间；检查能否减少逐块屏障。偏移扫描也可以尝试并行实现，但中心数较少时，串行代码可能更便宜。

**预期目标。**降低非矩阵计算阶段的时间，更快完成一次划分并生成叶块任务。

**验证指标。**各阶段时间、原子冲突、屏障等待、单位成员分发成本和后续叶块就绪时间。修改时需要检查成员归属、计数、写入边界、任务发布顺序及可见性，避免遗漏或重复发布。

依据：[COUNT 计数提交](/home/wbh/rswork/SHEAR/shear-core/src/algorithm/pipnn/compute_backend.rs:15237)、[EMIT 偏移计算](/home/wbh/rswork/SHEAR/shear-core/src/algorithm/pipnn/compute_backend.rs:15395)、[SCATTER 分发](/home/wbh/rswork/SHEAR/shear-core/src/algorithm/pipnn/compute_backend.rs:15574)、[PUBLISH 发布](/home/wbh/rswork/SHEAR/shear-core/src/algorithm/pipnn/compute_backend.rs:15652)。

## 6. 工作领取粒度、边界填充与尾部任务

**当前做法。**大分区 CTA 批量领取最多 8 个成员块，再将块分给 warp。一次只领到 3 个块时，其余 warp 不参与这次矩阵计算。领取和后续推进以 CTA 为单位，没有让空闲 warp 独立领取另一个任务。叶块也按固定源点任务粒度拆分，最后一批可能不足。

**可能的问题。**小尾块不能填满 CTA；矩阵行数、列数或维度未对齐时，需要填充；耗时不同的任务会产生执行尾部。一批任务全部被领取，也不代表全部完成，此时其他 CTA 仍可能找不到新工作。

**优化思路。**按任务大小选择领取数量或 CTA 配置，将多个小任务合批，或测试更细粒度的工作分配。不同分区有不同 leader 集合，不能简单拼成一个统一距离矩阵；合批时仍需保留各自的数据与结果边界。

**预期目标。**减少尾部和边界上的无效工作，同时控制队列领取与任务描述开销。

**验证指标。**每次实际领取块数、每个 CTA 的有效源点数、矩阵块有效位置比例、任务时长分布、最后一批任务的完成时间和队列操作次数。

依据：[分区 warp 与成员块映射](/home/wbh/rswork/SHEAR/shear-core/src/algorithm/pipnn/compute_backend.rs:14727)、[批量领取](/home/wbh/rswork/SHEAR/shear-core/src/algorithm/pipnn/compute_backend.rs:15138)、[叶块源点分工](/home/wbh/rswork/SHEAR/shear-core/src/algorithm/pipnn/compute_backend.rs:10535)。

## 7. staged 模式的局部结果合并与锁等待

**当前做法。**`row-owned` 让一个任务负责一组源点的全部候选范围，直接输出该叶块内的 top-k。`staged` 则进一步拆分候选列，同一个源点会产生多份局部 top-k，再通过每行一把锁进行合并。这里的源点所有权是叶块内的任务所有权，不是全局图中该点的唯一所有权。

**可能的问题。**staged 增加可并行任务，也增加了任务领取、重复读取和局部结果合并。处理同一源点的任务同时完成时，可能竞争行锁。GPU 在轮询时虽有线程活动，但没有推进有效结果。

**优化思路。**根据叶块大小、维度、k 和当前任务供给选择两种模式；对较小叶块或任务已经充足的情形，评估避免额外列拆分；测试由指定任务归并或分阶段归并局部结果。替代方式可能增加临时存储、全局内存流量和阶段等待，需要一起比较。

当前 auto 策略在满足 dense SQ8、维度对齐、`k≤4`、无精确重排和无审计等条件下，对 padded dimension 不超过 256 的情况选择 row-owned，其余选择 staged。当前选择逻辑没有直接使用叶块大小或即时队列状态。

**预期目标。**在任务并行度与合并开销之间找到更合适的执行方式。

**验证指标。**局部任务数、行锁轮询次数、合并耗时、临时存储、叶块计算时间和整体构建时间。比较同一批叶块、同一候选集合上的输出一致性；不能把仓库中的正确性测试代码或运行配置视为已有的性能对照结果。

依据：[执行模式选择](/home/wbh/rswork/SHEAR/shear-core/src/algorithm/pipnn/compute_backend.rs:578)、[行锁归并](/home/wbh/rswork/SHEAR/shear-core/src/algorithm/pipnn/compute_backend.rs:7261)、[任务完成后的输出分支](/home/wbh/rswork/SHEAR/shear-core/src/algorithm/pipnn/compute_backend.rs:10915)。

## 8. 分区生产与候选消费的供给匹配

**当前做法。**分区 CTA 产生叶块任务，候选 CTA 消费叶块任务。候选队列暂时为空时，候选 CTA 可以协助共享大分区任务。但是否有可协助的工作，取决于分区阶段、未领取块数和任务状态。

**可能的问题。**候选任务未就绪时可能等待；某些分区阶段只有少量线程推进，不能为全部候选 CTA 提供工作；执行尾声可能只剩少数长任务。已有协作机制缓解这些问题，但不保证任意时刻所有 CTA 都有有效任务。

**优化思路。**根据队列供给和任务代价调整协作时机、任务顺序或角色配额；比较优先生成可执行叶块与优先处理大分区的取舍。更复杂的动态策略也有状态管理和调度成本，不应预设优于当前实现。

**预期目标。**缩短无任务等待和执行尾部，让分区与候选计算持续推进。

**验证指标。**叶块队列深度、空队列等待、首次叶块就绪时间、协作工作量、任务完成时间分布，以及整个子树的 GPU event 时间。还应区分内核内部无任务，与子树之间因加载、传输或主机处理造成的 GPU 空档。

依据：[候选 CTA 协助大分区](/home/wbh/rswork/SHEAR/shear-core/src/algorithm/pipnn/compute_backend.rs:17250)。

## 9. 向量加载、缓存复用与资源占用

**当前做法。**根据成员 ID 获取量化向量、尺度和范数，再将维度分片装入共享内存，供 WMMA 使用。线程还维护候选状态和矩阵片段。矩阵计算形状规则，不意味着所有向量在物理存储中都连续，也不意味着数据准备没有成本。

当前 dense SQ8 向量采用“向量 ID × 连续维度”的存储方式。A 按行解释、B 按列解释来完成点积，这种搭配本身正确；B 的列式解释并不意味着需要先对全部向量做一次物理转置。不能仅凭行式或列式名称判断布局优劣。

**可能的问题。**一个向量内部的维度连续，但 tile 中的成员由 ID 间接指定，不同向量可能位于相隔较远的位置。不同 warp 处理不同源点时可能重复加载相同的 leader/候选；在当前“目标块外循环、维度片内循环”的实现中，同一批源向量也会随目标块变化再次经过加载循环。这些请求可能被缓存部分吸收，不能直接等同于重复访问显存。

此外，数据未及时就绪会产生等待；共享内存和寄存器需求可能限制一个 SM 同时驻留的 CTA 数量。候选数组最终使用多少寄存器、是否溢出到局部内存，需要编译报告与 profiler 确认。

**优化思路。**检查是否适合预先打包 leader 数据、采用向量化搬运、跨 warp 复用目标块，或在一次加载源数据后计算多个目标块；评估下一维度片的预取与当前计算重叠，以及针对常用小 k 缩减状态。预打包本身有成本，跨 warp 共享可能需要更多 CTA 同步，保留多个结果块或双缓冲也会增加资源占用，需评估整体效果。

**预期目标。**减少重复加载和数据等待，在资源开销可控的条件下提高有效吞吐。

**验证指标。**全局内存读取量、缓存命中、内存依赖等待、寄存器与共享内存占用、局部内存访问、驻留 CTA 数及内核时间。较高的 occupancy 只能作为参考，不能替代时间和有效吞吐指标。

依据：[分区 WMMA 数据加载与维度循环](/home/wbh/rswork/SHEAR/shear-core/src/algorithm/pipnn/compute_backend.rs:14811)、[叶块中间状态](/home/wbh/rswork/SHEAR/shear-core/src/algorithm/pipnn/compute_backend.rs:10571)。

## 10. WMMA 结果布局与后处理访问方式是否匹配

**当前做法。**通用 SQ8 路径把 16×16 的 INT32 累加结果通过 `store_matrix_sync(..., mem_row_major)` 按行存入共享内存。后处理的前 16 个线程各负责一个源点，在同一次列循环中读取：

```cpp
int dot = c_tile[lane * 16 + local_col];
```

每个线程单独看是在顺序读取一行，但同一时刻相邻线程之间相隔 16 个整数，即 64 字节。分区和通用 SQ8 叶块的结果处理均存在这一访问模式。

**静态分析发现。**按照现代 NVIDIA GPU 的 32 个共享内存 bank、相邻 32 位字映射到相邻 bank 的规则，固定列 `col` 时：

```text
bank = (共同基地址的 bank 偏移 + 16 × lane + col) mod 32
```

以基地址偏移和 `col` 都为 0 举例：

| 活跃线程 | 访问的整数下标 | bank |
|---|---:|---:|
| lane 0 | 0 | 0 |
| lane 1 | 16 | 16 |
| lane 2 | 32 | 0 |
| lane 3 | 48 | 16 |
| … | … | … |
| lane 15 | 240 | 16 |

在这组逐项 32 位加载中，16 个线程集中到两个 bank，每个 bank 对应 8 个不同地址。这里不是多个线程读取同一地址的广播情形，而是存在潜在的 8 路加载 bank 冲突。这个结论来自源码地址映射分析，实际生成的加载指令、冲突次数与耗时仍需检查。

**可能的问题。**共享内存加载被拆为更多访问步骤，使距离恢复与 top-k/top-r 后处理更慢。不能由此推断整个内核变慢 8 倍，也不能把它直接推广到所有专用内核或 WMMA 的 A/B 片段加载。

**优化思路。**对照测试将 C 结果按列存储，并同步修改读取下标：

```cpp
// 待验证方案：存储与读取必须同时改变。
wmma::store_matrix_sync(c_tile, acc_frag, 16, wmma::mem_col_major);
int dot = c_tile[local_col * 16 + lane];
```

这样在固定列下，相邻活跃线程读取相邻整数。它改变的是结果的物理存储方式，不改变距离矩阵的数学含义。还需要确认所有相关读取位置都使用匹配的下标，并比较列式写出的成本；不能只改读取下标。若考虑 padding 或其他布局，也必须满足 WMMA 接口的对齐和 leading dimension 要求。

**预期目标。**让结果布局与消费结果的线程分工匹配，降低共享内存访问冲突。

**验证指标。**先检查实际机器指令，再比较对应共享内存加载的 bank 冲突或额外 wavefront、结果写出和后处理时间、整个内核时间及候选结果一致性。静态映射检查不能替代 GPU 实测。

依据：[分区结果存储与读取](/home/wbh/rswork/SHEAR/shear-core/src/algorithm/pipnn/compute_backend.rs:14875)、[叶块结果读取](/home/wbh/rswork/SHEAR/shear-core/src/algorithm/pipnn/compute_backend.rs:10046)、[NVIDIA 共享内存与 bank 说明](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/writing-cuda-kernels.html)。

## 11. partition 中的分支分歧与 top-r 维护

### 11.1 应分析分支分歧，而非 CPU 式分支预测失误

GPU 上应重点关注同一 warp 的线程是否因条件不同而执行不同路径，以及有多少 lane 执行有效工作。短条件可能被编译器转换为谓词执行，因此源码中的 `if` 不必然对应昂贵的分支。不同 warp 执行不同路径，也不等于同一 warp 内发生分歧。[NVIDIA 分支与谓词说明](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#branching-and-divergence)

| 条件或操作 | 当前主要性质 |
|---|---|
| 判断 COUNT、SCATTER 等阶段 | CTA 共享阶段快照，通常是统一控制流 |
| `warp >= tile_count` | 一个 warp 内条件一致，反映工作不足 |
| `lane < 16` 或尾块的有效成员判断 | 只有部分 lane 有效，影响线程分工和边界利用率 |
| 候选距离是否优于当前最差项 | 与各源点的数据相关，可能产生不同执行路径 |
| top-r 插入时需要移动多少项 | 不同线程可能有不同循环次数 |
| 距离接近时执行 tie-break | 部分线程需要额外的哈希与比较 |
| 不同成员写入不同子分区 | 主要涉及写地址分散和原子竞争，不一定是分支分歧 |

依据：[CTA 阶段快照](/home/wbh/rswork/SHEAR/shear-core/src/algorithm/pipnn/compute_backend.rs:15107)、[warp 任务有效性判断](/home/wbh/rswork/SHEAR/shear-core/src/algorithm/pipnn/compute_backend.rs:14727)、[成员分发](/home/wbh/rswork/SHEAR/shear-core/src/algorithm/pipnn/compute_backend.rs:15604)。

### 11.2 更明确的检查对象是 top-r 插入和 tie-break

**当前做法。**分区计算得到距离后，先判断候选是否值得保留，再逐项比较、移动并插入。距离差落在容差内时，使用基于点与 leader 的哈希进行 tie-break。不同线程负责不同成员，因此保留、拒绝、移动和 tie-break 的执行情况可能不同。

**可能的问题。**同一 warp 内的有效指令路径可能不一致，动态插入和数组索引也可能增加指令或状态开销。但提前拒绝候选能省去后续处理，按需计算 tie-break 也避免了对全部候选计算哈希；不能假设去掉这些分支一定更快。

**优化思路。**针对常见 `fanout=1`、`fanout=3` 测试专用实现，比较固定次数的比较交换、循环展开与当前提前退出逻辑。必须核对距离容差、比较顺序、tie-break 和最终结果；尤其不能仅因为换用同一个比较函数，就假定不同比较次序一定产生相同分区。

**预期目标。**在保持分区语义的前提下，减少不必要的控制流和候选维护开销。

**验证指标。**生成的分支或谓词指令、活跃 lane、插入与拒绝比例、移动次数、tie-break 频率、top-r 输出一致性及分区阶段时间。应覆盖距离相同或接近的输入，避免只在容易区分的距离分布上验证。

依据：[top-r 插入逻辑](/home/wbh/rswork/SHEAR/shear-core/src/algorithm/pipnn/compute_backend.rs:6524)、[固定容量入口](/home/wbh/rswork/SHEAR/shear-core/src/algorithm/pipnn/compute_backend.rs:6597)。

## 12. 建议的验证顺序

1. **先固定基线并检查运行路径。**记录代码版本、GPU、编译选项、数据规模和维度、k、fanout、leaf mode、ticket batch、叶块分布与实际启用的内核。区分配置值、实现值和运行时观测值。
2. **先定位具体阶段。**优先测量 SCATTER、WMMA 后处理和 staged 合并；其中 WMMA 后处理应先检查第 10 节的结果布局疑点，因为其地址映射依据明确。再核对输入块复用与 top-r 分歧开销。目前没有证据证明其中哪一处占时最大，应根据测量结果决定修改顺序。
3. **对保持候选集合不变的改动，先做同任务对照。**例如调整搬运线程分工或 top-k 归并方式，先验证候选与距离结果，再比较阶段和内核时间。
4. **对改变分区的改动，额外验证检索质量。**leader 数量、小块合并和划分策略会改变候选集合，需要比较召回率/QPS、图大小、构建时间和内存占用。
5. **收益最终回到整体构建时间。**局部加速可能被其他阶段掩盖；复杂策略只有在整体收益与实现成本相称时才值得保留。

当前部分计时器累计的是不同 CTA 或线程上的 `clock64()` 差值，其作用范围和累加次数可能不同；例如行锁计时包含等待与合并。不能将这类累计值直接除以 GPU event 时间，解释成某操作的端到端耗时占比，也不能把并发阶段的累计时间直接相加得到总时间。

历史 profile 若来自不同代码版本、TF32 路径或其他内核，也不能直接用来断言当前 SQ8 路径的瓶颈比例。需要先确认代码路径、配置与计时定义一致。
